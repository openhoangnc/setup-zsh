# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A macOS-only Zsh setup distributed as `curl … | bash`. There is no build system, no
dependency manifest, and no test suite — the deliverables are four shell scripts plus
vendored zsh plugins. Everything the user ends up with is generated by `setup.sh` at
install time, so **`setup.sh` is the source of truth for the shell configuration**, not
any file under `~`.

## Commands

```bash
bash -n setup.sh && bash -n uninstall.sh && bash -n bin/install-dev-tool && bash -n bin/git-sync
```

```bash
bash setup.sh
```

Running `setup.sh` from a clone installs from the local `plugins/` and `bin/` (it checks
`$SCRIPT_DIR`); run from a pipe it downloads `main.zip` from GitHub instead. That is the
deploy step for changes to `bin/*` — they are copied to `~/.zsh/setup-zsh/bin/`, which
`~/.zshenv` puts on `PATH`.

```bash
bash bin/install-dev-tool
```

Run the installer straight from the working tree to test changes without deploying.
Flags: `-u/--update-all` (select every outdated tool, install, exit), `-a/--all`,
`-h/--help`. Startup fires ~18 parallel `curl` version probes, so it needs network.

```bash
bash uninstall.sh
```

Removes the `~/.zshrc` block and `~/.zsh/setup-zsh/`. Note the asymmetry: it does **not**
strip the `setup-zsh` block `setup.sh` writes into `~/.zshenv`.

## Architecture

### Install layout and the marker-block contract

Everything lands under `~/.zsh/setup-zsh/`: `plugins/` (isolated from `~/.zsh/plugins`),
`bin/` (on `PATH`), `env.zsh` (generated env), `install.log`.

Three files are edited in the user's home, each idempotently via delimiter blocks stripped
with `awk` before being re-appended:

- `~/.zshrc` — `# >>> setup-zsh >>>` … `# <<< setup-zsh <<<`: interactive-only config
  (history, keybindings, completion, plugins, prompt, LS colors).
- `~/.zshenv` — same markers: environment only (`PATH`, sources `env.zsh`). This is what
  makes tools resolve for non-interactive shells, IDEs and `zsh -c`.
- `~/.zsh/setup-zsh/env.zsh` — per-tool blocks `# >>> Go >>>` … `# <<< Go <<<`.

The `~/.zshrc` block *also* sources `env.zsh` at the end. That is deliberate (see the
comment in section 9 of `setup.sh`): hosts that spawn `zsh --no-rcs` and then source
`~/.zshrc` never run `~/.zshenv`. `typeset -U path PATH` absorbs the duplication.

`env.zsh` blocks are written by two independent implementations that must stay in
agreement: `_update_env_block` in `setup.sh` (which only fills in blocks that are missing,
guarded by `_needs_env_block`) and `update_env_block` in `bin/install-dev-tool` (which
rewrites its block on every install). Changing the block format means changing both.

Both `~/.zshrc` and `~/.zshenv` are backed up to `*.bak.<timestamp>` only when the content
actually changed, so re-running `setup.sh` doesn't litter backups.

### `setup.sh` — the zshrc payload

Most of the file is a single quoted heredoc (`<< 'EOF'`) containing the zshrc block, so
nothing inside it is expanded at install time — write it as the shell code the user will
run. The substantial logic in there is the **match-any autosuggestion strategy**: it adds
a `match_any` strategy and then *overrides zsh-autosuggestions internals* —
`_zsh_autosuggest_fetch_suggestion`, `_zsh_autosuggest_suggest`, `_zsh_autosuggest_accept`,
`_zsh_autosuggest_execute`, `_zsh_autosuggest_partial_accept` — to support case-insensitive
substring suggestions displayed after a `»` marker. Upgrading the vendored
`plugins/zsh-autosuggestions` can silently break these overrides; re-check them against the
plugin's own definitions when bumping it.

### `bin/install-dev-tool` — TUI installer

One ~2000-line bash script with a fixed pipeline:

1. **Version probes** — a block of `( … ) &` subshells, each `curl … | grep/cut` for one
   tool's latest version into `$TEMP_VER_DIR/<tool>`; `show_spinner` waits on `jobs -r`.
   Results are read into `LATEST_*` and empty values are normalized to `Unknown`.
2. **Per-tool triads** — `detect_<tool>` (installed version from disk, never from `PATH`
   where that would misreport — see `detect_jdk`), `format_status` / bespoke formatters,
   and `install_<tool>`. GUI apps go through `install_app_bundle`, which stages into
   `/Applications/.X.app.staging` before swapping so a failed copy can't delete the app.
3. **Menu state** — selections are flat numbered variables `SEL_1 … SEL_N` driven through
   `eval` (bash 3.2 has no associative arrays), plus a `CURSOR` that indexes tool rows
   first and the bottom action row after them.

**Versions and downloads come straight from each vendor**, never from Homebrew's API
(`formulae.brew.sh`): the vendor's own update feed or download page (Sparkle appcast,
electron-updater manifest, release JSON), or the vendor's GitHub releases where that is
how it ships (DBX, Bun, uv, Temurin). When the download URL can't be rebuilt from the
version (codenames, build ids), the probe writes it to `$TEMP_VER_DIR/<tool>_url` and the
installer uses that, so the version shown and the build installed can never disagree.

`is_outdated` is the single comparison rule: an install *newer* than the reported latest is
never treated as outdated, so the tool never suggests a downgrade.

Adding a tool touches roughly ten places, all of which must agree: the header comment, a
version-probe subshell, the `LATEST_*` read and the normalization loop, `detect_*`,
`refresh_installed_tools`, the menu row, `toggle_all` / `select_outdated` /
`has_outdated_tools` / the two `count` loops (all `{1..N}` ranges), `installed_version_for`,
the `SEL_*` init and reset lines, `max_cursor` and the UP/DOWN/LEFT/RIGHT and SPACE/ENTER arithmetic, the
two-digit number-key branch, the up-to-date `confirm_reinstall` guard, and the numbered
`install_*` call inside the logged batch. Inserting in the middle renumbers every later
item; appending at the end does not.

Each batch truncates `~/.zsh/setup-zsh/install.log` and `tee`s into it, so only the last
run is kept. After the batch the menu returns on its own unless there is something to
read first — a first-time install (decided by `installed_version_for`, which reports the
row's currently installed version) or an error found in that log.

Row 19 ("Global Packages") updates the *packages* the managers installed rather than the
managers themselves. The supported managers are listed in `GLOBAL_PM_ORDER`; each is
driven by a triple of `<pm>_bin` (resolver, applies guards — Yarn must be classic, `gem`
must not be the system Ruby, `cargo` needs the `cargo-install-update` plugin),
`pm_upgrade_<pm>`, and `pm_detail_<pm>`, plus an optional `pm_cleanup_<pm>`. `update_global_packages`, `show_globals_details`,
and `detect_global_pms` all just loop `GLOBAL_PM_ORDER` and skip any manager whose
resolver returns empty, so adding a manager means adding those three functions plus its
name to the order string — nothing else. JS managers run through `run_js_pm`, which puts
the right global bin dir on PATH (and exports `PNPM_HOME` for pnpm, without which pnpm
refuses to touch globals).

Only npm and Homebrew are cheap enough to poll at startup, so they alone carry the
headline count in the menu (`npm_outdated_list`, `brew_outdated_count`, launched by
`spawn_global_checks` alongside the version probes) and are the only signal `globals_outdated`
uses for `[U]`. The rest are updated on demand; an empty npm/brew count means the check
failed — never "nothing to update". After the upgrade loop, `update_global_packages` runs a best-effort cache-cleanup pass
(`npm cache clean`, `pnpm store prune`, `brew cleanup`, `uv cache prune`, `gem cleanup`,
`composer clear-cache`, ...): it calls `pm_cleanup_<pm>` for every manager that defines one
(guarded by `declare -f`, so pipx/cargo are skipped), and cleanup failures only warn — they
never flip `$failed`, so they can't force the post-batch pause. The full per-manager
breakdown is computed lazily by `show_globals_details`, opened with **Enter** on row 19
(Space and the `19` key still toggle selection — the `SPACE|ENTER` case special-cases
`action = ENTER` on that row).

### `bin/git-sync`

Standalone; installed on `PATH` so Git also exposes it as `git sync`. Fast-forwards
main/master and develop/dev to their upstreams, never force-updates diverged branches, and
with `--cross` merges the two into each other using `git merge-tree` plumbing so no branch
is checked out and the working tree is untouched. Not documented in the READMEs.

## Conventions

- **Target `/bin/bash` 3.2** (what macOS ships). No associative arrays, `mapfile`,
  `${var,,}`, or `&>>`. The `eval`-driven `SEL_N` pattern exists for this reason.
- **BSD userland.** Notably `mktemp` only substitutes *trailing* `X`s, so templates never
  carry an extension (`mktemp /tmp/go.XXXXXX`, not `go.XXXXXX.tar.gz`); `tar`/`unzip`/
  `hdiutil` read magic bytes anyway.
- **Indentation is per-file**: tabs in `setup.sh`, `uninstall.sh`, `bin/git-sync`;
  four spaces in `bin/install-dev-tool`.
- **Comments explain *why*, at length, where a line looks wrong but isn't** (BSD `mktemp`,
  the JDK build-suffix trim, the Android Studio version truncation, `⛅` vs `☁️` for
  terminal cell width, the `--no-rcs` fallback). Match that density when adding similar
  workarounds.
- **Four READMEs** (`README.md`, `README_JA.md`, `README_VI.md`, `README_ZH.md`) mirror one
  another; a user-visible change should update all four.
- **Commits** follow `type(scope): summary`, e.g. `feat(install-dev-tool): add gcloud CLI`.
